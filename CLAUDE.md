# CLAUDE.md — kosynka-backend

Отвечай по-русски. Комментарии и docstring-и в коде — по-русски.

**Все идентификаторы — только латиницей.** Классы, функции, переменные, аргументы,
фикстуры и имена тестов: `def test_coefficient_clamped_on_both_sides`, а не
`def test_коэффициент_ограничен_с_обеих_сторон`. Русские имена тестов в репозитории
были и вычищены — не возвращай их.

## Зачем этот проект существует

Косынка (Klondike) без рекламы для пожилого человека. Это не абстрактное требование, а критерий
всех решений: приложение делается для конкретной бабушки, которая играет неспешно, плохо попадает
пальцем и не будет ничего настраивать.

Из этого следуют вещи, которые **не обсуждаются**:

- Никакой рекламы, аналитики, трекинга, рекламных SDK — ни при каких обстоятельствах.
- Никакой обязательной регистрации: ни email, ни пароля, ни экрана входа.
- Игра работает полностью офлайн. Сеть — опциональное дополнение, а не условие работы.
- Никаких тёмных паттернов: энергии, стриков, пушей «вернись», таймеров давления.

## Стек и границы

Python 3.12. Берём самые свежие стабильные версии — на момент написания это:

| Что | Версия | Ограничение в `pyproject.toml` |
|---|---|---|
| FastAPI | 0.140.13 | `>=0.140,<0.141` |
| uvicorn[standard] | 0.52.0 | `>=0.52,<0.53` |
| pydantic-settings | 2.14.2 | `>=2.14,<3.0` |
| SQLAlchemy[asyncio] | 2.0.51 | `>=2.0,<3.0` |
| greenlet | 3.5.4 | `>=3.5,<4.0` |
| asyncpg | 0.31.0 | `>=0.31,<0.32` |
| Alembic | 1.18.5 | `>=1.18,<2.0` |
| PostgreSQL | 18.4 | образ `postgres:18` |

Pydantic 2.13.4 приходит транзитивно через FastAPI и pydantic-settings, отдельно не
объявлен. `pyproject.toml` — в формате PEP 621 (`[project]`), как принято в Poetry 2.x;
dev-зависимости остаются в `[tool.poetry.group.dev.dependencies]`.

Версия Postgres одна и та же в `docker-compose.yml`, в CI-сервисе для `tests/api` и в стенде —
расхождение мажора ловится не тестами, а продом. SQLAlchemy только 2.x-стиль (`Mapped`,
`mapped_column`, `select()`), legacy Query API не использовать. Pydantic только v2.

Зависимости и виртуальное окружение — **Poetry**; `pip install` в этом репозитории не используется.

Доставка: пуш в `main` → GitHub Actions → образ в GHCR → ssh → `docker compose up -d`
на одном сервере. Три контейнера: Caddy, приложение и PostgreSQL 18.
Наружу смотрит только Caddy — он же терминирует TLS.
Подробности разовой настройки сервера — в `docs/deploy.md`.

Мобильный клиент — отдельный репозиторий: **Unity**. Выбран за гибкость игровой
механики. Следствие, о котором нельзя забыть: Unity рисует интерфейс сам и
системные настройки доступности не наследует, поэтому масштаб шрифта и размеры
областей нажатия клиент обязан читать из системы и применять сам — иначе
теряется главное требование проекта.

Аналитика и телеметрия Unity Gaming Services вырезаются и не возвращаются:
правило «никакого трекинга» действует и на движок.

На бэкенд выбор клиента не влияет — API остаётся обычным HTTP с JSON.

## Текущая итерация

**Итерация 1 (сейчас):** регистрация устройства по токену, начисление опыта за победу, уровни.

Что осознанно **не** реализовано и не должно появляться без явной просьбы:

- Лидерборд, раздача дня, рейтинги, ники.
- Валидация партий пересчётом на сервере.
- Восстановление аккаунта, привязка к Google, синхронизация между устройствами.
- Режим draw-3, статистика, достижения.
- Redis, очереди, кеши, WebSocket, GraphQL.

Поля `deal_cards` и `replay` уже принимаются и складываются в базу **без проверки** — это
намеренный задел на итерацию 2. Не удаляй их и не начинай валидировать по своей инициативе.

## Уже принятые решения (не переоткрывать)

| Решение | Почему |
|---|---|
| Уровень **не хранится**, выводится из `xp_total` формулой | перебалансировка кривой не требует миграции игроков |
| Каждая партия помнит `xp_formula_version` | возможность пересчитать опыт задним числом |
| Опыт начисляется атомарным `UPDATE ... RETURNING` | нет read-modify-write, нет гонок, не нужен `SELECT FOR UPDATE` |
| Идемпотентность по `(player_id, client_game_id)` | мобильная сеть ретраит; опыт не должен удваиваться |
| `device_id` отделён от токена | токен не истекает, но теряется при переустановке; без device_id прогресс не вернуть. Цена: кто предъявит чужой device_id, заберёт аккаунт — закрывается только входом через Google, а он в итерации 2 |
| В базе `sha256(token)`, не сам токен | токен показывается ровно один раз при регистрации |
| Коэффициент времени ограничен сверху `k_max=2.0` | одновременно баланс и защита: `duration_ms=1` даёт максимум ×2, а не ×100 |
| Параметры кривой — в переменных окружения, не в коде | правятся без пересборки образа |
| `/healthz` не трогает базу, `/readyz` трогает | иначе моргнувший Postgres перезапустит все поды разом |
| PostgreSQL один, без реплик и без Redis | нагрузка микроскопическая; сложность дороже задачи |
| Один сервер, `docker compose`, **без Kubernetes** | на одной ноде k8s не даёт ни планирования, ни HA, ни нужного автоскейлинга — только вдвое больше эксплуатации |
| Простой на секунды при выкатке допустим | игра работает офлайн, сеть опциональна; zero-downtime — единственное, ради чего тут терпели бы k8s, и оно не нужно |
| PostgreSQL контейнером на том же сервере, не managed | managed стоит дороже самой ВМ; бэкапы владелец делает сам через `pg_dump` |
| База наружу не публикуется | до неё достаёт только приложение по compose-сети; порт 5432 снаружи закрыт |
| Домен — бесплатный поддомен DuckDNS | покупать не стали; на голый IP Let's Encrypt выдаёт только 6-дневные сертификаты, требующие присмотра, которого у проекта не будет |
| TLS — Caddy с автоматическим ACME | получает и продлевает 90-дневный сертификат сам, без внешних клиентов и таймеров |
| Деплой ровно на пуш в `main` | одна ветка, одно окружение; отдельного stage нет и не нужно |
| Тесты и деплой в одном workflow | джоба `deploy` стоит за `needs: quality` — раскатиться в обход красных тестов нельзя |
| Образ тегается sha коммита, не `latest` | видно, что именно крутится, и возможен откат одной строкой |
| Логика деплоя — в `deploy/release.sh`, не в yaml | её видно целиком и можно прогнать руками, когда что-то пошло не так |

**Токен не защищает от читеров.** Он отвечает на вопрос «кто это», а не «правда ли он выиграл».
Пока лидерборда нет, накрутивший уровень обманул только себя. Не изобретай подпись запросов,
обфускацию и TLS-пиннинг — ключ всё равно лежит в APK. Единственная реальная защита —
пересчёт партии на сервере, и она относится к итерации 2.

## Структура

```
app/            # слои: api → services → single_object → views → schemas
  xp.py         # формула опыта и кривая уровней. ЧИСТЫЙ модуль
  config.py     # pydantic-settings, префикс KOSYNKA_; get_xp_config()
  db.py         # async engine, sessionmaker, get_session
  models.py     # SQLAlchemy 2.0 declarative: Player, Game + NAMING_CONVENTION
  security.py   # генерация токена, хеш, зависимость current_player
  exceptions.py # фабрики HTTPException: raise_unauthorized, raise_game_not_found
  api/          # РОУТЫ: players.py, games.py, meta.py. Логики ноль
  services/     # оркестрация: сходить в single_object, отдать во views
  single_object/# ВЕСЬ SQL. Возвращает модели и скаляры, не схемы
  views/        # доменные объекты → схемы ответа, make_*_response_schema
  schemas/      # pydantic-контракты запросов и ответов
alembic/        # миграции
tests/unit/     # без базы и сети
tests/api/      # против настоящего Postgres
deploy/         # то, что лежит на сервере в /opt/kosynka; CI кладёт rsync-ом
  docker-compose.yml     # caddy + app + db (postgres:18)
  Caddyfile              # реверс-прокси и TLS
  release.sh             # pull → миграции → up -d → ждать healthcheck
  cloud-init.yaml        # user-data для создания сервера; хостеру отдаётся ОН, не compose
.github/workflows/ci.yml # quality → deploy (доставка живёт здесь)
.gitlab-ci.yml  # только линтеры и тесты, без деплоя
docs/deploy.md  # разовая настройка сервера
docs/tls.md     # как устроен TLS; запасной путь — сертификат на голый IP
docker-compose.yml # ЛОКАЛЬНЫЙ: db + app с --reload. С серверным не путать
Dockerfile      # multi-stage: poetry-слой отдельно от исходников
pyproject.toml  # зависимости (Poetry) + настройки ruff, mypy, pytest
poetry.lock     # коммитится; воспроизводимость сборки держится на нём
```

**`app/xp.py` не должен импортировать ни FastAPI, ни SQLAlchemy, ни настройки.** Он принимает
`XpConfig` параметром и тестируется без окружения. Это ядро домена; если тянет добавить туда I/O —
значит, логика поехала не туда.

## Команды

```bash
# зависимости
poetry install                            # всё, включая dev-группу
poetry install --only main --no-root      # так ставит образ и CI-джобы без тестов

# тесты
poetry run pytest tests/unit -q           # секунды, без базы
poetry run pytest tests/api -q            # нужен живой Postgres; DSN берётся из .env

# качество
poetry run ruff check app tests && poetry run ruff format --check app tests
poetry run mypy app

# миграции
poetry run alembic upgrade head
poetry run alembic check                  # расхождение моделей и миграций
poetry run alembic revision --autogenerate -m "..."

# локально целиком, тем же способом, что на сервере
docker compose up --build                 # :8000, миграции отдельным шагом до старта app
docker compose down -v                    # остановить и снести данные базы

# быстрый цикл разработки (без контейнера, с автоперезагрузкой)
poetry run uvicorn app.main:app --reload  # :8000, DSN из .env

# compose-файлы разбираются без ошибок
docker compose config -q                  # локальный
docker compose -f deploy/docker-compose.yml config -q

# что крутится на сервере
ssh deploy@SERVER 'cd /opt/kosynka && docker compose ps'
ssh deploy@SERVER 'cd /opt/kosynka && docker compose logs -f --tail=100 app'
```

Перед коммитом должно быть зелено: `ruff`, `mypy`, `pytest`, `alembic check`, `poetry check --lock`.

## Правила изменений

1. **Меняешь модель — пиши миграцию в том же коммите.** `alembic check` в CI валит пайплайн
   при расхождении, и это уже ловило реальный баг (nullable у timestamp-колонок).
2. **Новая ручка — новый тест в `tests/api/`.** Тест на успех, на 401 и на идемпотентность,
   если ручка что-то создаёт.
3. **Методы получения одного объекта в `single_object` принимают `raise_exception`.**
   По умолчанию `True`: не нашли — бросили ошибку прямо в слое доступа, и сервис
   не проверяет результат на `None`. Кому отсутствие объекта — нормальный путь
   (регистрация по `device_id`), тот передаёт `raise_exception=False` явно.
   Перегрузки по `Literal[True]`/`Literal[False]` дают точный тип возврата,
   иначе `mypy --strict` требовал бы проверки на `None` там, где её быть не должно.
4. **У каждого роута — `response_model` в декораторе и аннотация возврата.** Первое задаёт
   контракт и фильтрует ответ, второе требует `mypy --strict`. Класс в `response_model` —
   ровно тот, что возвращает соответствующий `make_*_response_schema` из `app/views/`:
   роут не собирает ответ сам и не отдаёт `dict`.
5. **Правишь `app/xp.py` — добавь опорные точки в `tests/unit/test_xp.py`.** Там уже есть
   параметризованная таблица «минуты → опыт», дополняй её, а не переписывай.
6. Новая переменная окружения → `Settings` + `deploy/docker-compose.yml` одновременно
   (и локальный `docker-compose.yml`, если она нужна в разработке).
7. **Секреты не попадают в git вообще.** Они живут на сервере в `/opt/kosynka/.env.app`
   и `.env.site`, созданных руками один раз. `rsync` в деплое идёт с `--exclude='.env*'`,
   чтобы выкатка их не затирала.
8. Не добавляй зависимости без нужды. Каждая новая строка в `pyproject.toml` требует
   обоснования: что она делает такого, чего нет в стандартной библиотеке или уже стоящих пакетах.
   Добавлять — только через `poetry add` (инструменты разработки — `poetry add --group dev`),
   не правя `pyproject.toml` руками; `poetry.lock` идёт в том же коммите, что и `pyproject.toml`.

## Известные ловушки

- **`KOSYNKA_DB_POOL_SIZE` не должен упираться в `max_connections`.** У `postgres:18`
  по умолчанию 100, так что запас есть, но в него же лезет разовый запуск миграций.
  Классическое место, где деплой выносит базу на ровном месте.
- **Пароль базы лежит в двух файлах на сервере** — `.env.db` и `.env.app`. Разойдутся —
  приложение получит `password authentication failed`. Меняются только вместе.
- **Том `caddy_data` терять нельзя**: в нём сертификаты и ACME-аккаунт. После удаления
  Caddy выпустит всё заново и может упереться в лимит Let's Encrypt — 50 сертификатов
  на домен в неделю.
- **`docker compose down -v` на сервере стирает том `pgdata`**, то есть весь прогресс
  игроков. Бэкапов никто не делает автоматически, это осознанная цена своей базы.
- `round()` в Python банковское: `round(2.5) == 2`. В `xp.py` округление сделано явно через `+0.5`,
  не «упрощай» обратно.
- `Depends(...)` в дефолтах аргументов — идиома FastAPI; `B008` для неё отключён в `pyproject.toml`,
  не переписывай сигнатуры ради линтера.
- **`greenlet` объявлен явно, не удаляй его как «лишний».** Экстра `sqlalchemy[asyncio]`
  тянет его не на всех связках платформы и версии Python — на 3.13/arm64 не подтянулся,
  и всё падало с `the greenlet library is required to use this function`.
- **В `postgres:18` том переехал** с `/var/lib/postgresql/data` на `/var/lib/postgresql`.
  По старому пути данные молча не сохраняются — контейнер поднимется, а база будет пустой.
- Порядок в `release.sh` обязателен: `alembic upgrade head` идёт **до** `up -d`. В этот
  момент старый код работает с новой схемой, поэтому миграции должны быть обратно
  совместимыми: сначала колонка nullable, обязательной — следующим релизом.
- Если миграция упала, `release.sh` завершается **до** `up -d`, и старая версия продолжает
  работать. Это не полусломанный деплой, а задуманное поведение.
- Откат (`IMAGE_TAG=<старый sha> docker compose up -d`) возвращает образ, но **не откатывает
  миграции**. Обратная миграция пишется руками — Alembic сам этого не сделает.
- Пакеты в GHCR по умолчанию приватные: без `docker login ghcr.io` на сервере
  `docker compose pull` упадёт с `denied: unauthorized`.
- Джоба `deploy` падает, пока в репозитории нет секретов `SSH_*`. Это ожидаемо
  до покупки сервера, а не поломка пайплайна.

## Если предлагаешь усложнение

Проект сознательно держится минимальным. Прежде чем добавлять слой, спроси себя: это нужно
сейчас или «на вырост»? Если на вырост — не добавляй, скажи об этом одной строкой и иди дальше.

Инфраструктура здесь — один сервер и `docker compose`, и это осознанный откат от k8s:
он был написан и выброшен, потому что на одной ноде не давал ничего, кроме удвоенной
эксплуатации. Не предлагай вернуть Kubernetes, оркестраторы, service mesh или отдельный
CI-раннер, пока не появится вторая нода и причина её иметь.
