## Схема БД: решения, которые не переоткрываются

### players

| Колонка | Тип | Почему так |
|---|---|---|
| `id` | UUID PK | последовательный ключ выдавал бы число игроков и порядок регистрации |
| `device_id` | VARCHAR(128) NULL UNIQUE | идентичность устройства, отделённая от учётных данных |
| `token_hash` | VARCHAR(64) NOT NULL UNIQUE | `sha256(token)` в hex; сам токен не хранится |
| `xp_total` | INTEGER NOT NULL DEFAULT 0 | два дефолта: Python-side заполняет объект, server-side защищает `xp_total + n` от NULL |
| `created_at` | TIMESTAMPTZ NOT NULL | `timezone=True` и явный `nullable=False` обязательны |

**Колонки `level` нет и не должно быть.** Уровень выводится из `xp_total`
формулой, чтобы перебалансировка кривой не требовала миграции игроков.

**`updated_at` нет.** Он трогался бы на каждой победе и не отвечал бы ни на
один вопрос.

### games

| Колонка | Тип | Почему так |
|---|---|---|
| `id` | UUID PK | |
| `player_id` | UUID FK ON DELETE CASCADE | удаление игрока не должно упираться в его партии |
| `client_game_id` | UUID NOT NULL | ключ идемпотентности, генерирует клиент |
| `duration_ms` | BIGINT NOT NULL | INTEGER упёрся бы в 24.8 суток |
| `xp_awarded` | INTEGER NOT NULL | повтор обязан вернуть то же число; пересчёт дал бы другое, если кривую поменяли |
| `xp_formula_version` | INTEGER NOT NULL | партия помнит, по каким правилам посчитан её опыт |
| `deal_cards`, `replay` | JSONB NULL | задел на итерацию 2, **складываются без проверки** |
| `created_at` | TIMESTAMPTZ NOT NULL | момент приёма сервером, а не момент игры |

**Колонки `won` нет.** Ручка принимает только победы; хранение проигрышей —
это статистика, а она за пределами итерации 1.

**`deal_cards` и `replay` не валидировать и не удалять.** Тип в схеме —
`JsonValue`, то есть «любой валидный JSON». В модели — `JSONB(none_as_null=True)`:
без этого флага Python `None` пишется JSON-литералом `null`, и колонка никогда
не бывает SQL NULL.

### Ограничения — полный список

```
pk_players, pk_games
uq_players_token_hash              -- горячий путь аутентификации
uq_players_device_id               -- ключ идемпотентности регистрации
uq_games_player_id_client_game_id  -- ИДЕМПОТЕНТНОСТЬ партий
fk_games_player_id_players         -- ON DELETE CASCADE
```

Отдельного индекса по `games.player_id` нет: он ведущая колонка составного
UNIQUE, и тот же B-tree обслуживает выборку партий игрока.

Имена ограничений задаёт `NAMING_CONVENTION` в `app/models.py` — без неё
обратная миграция превращается в угадывание.

## Опыт и уровни

`app/xp.py` — **чистый модуль**: только стандартная библиотека, ни FastAPI,
ни SQLAlchemy, ни настроек. Параметры приходят в `XpConfig` аргументом.
Зависимость строго односторонняя: `config.py → xp.py`.

```
k  = target_seconds / (duration_ms / 1000)
k  = min(max(k, k_min), k_max)          # зажим с ОБЕИХ сторон
xp = int(base_xp * k + 0.5)             # округление явное, НЕ round()
```

- **`round()` запрещён**: он банковский, `round(62.5) == 62`, а нужно 63.
  В `tests/unit/test_xp.py` есть опорная точка ровно на этот случай (8 минут).
- **`k_min` — требование, а не украшение**: игра для человека, который играет
  неспешно, и партия на час не должна давать ноль.
- `duration_ms <= 0` возвращает `k_max`, а не исключение: чистая функция
  обязана быть тотальной.
- `XpConfig.__post_init__` отвергает `level_growth < 1.0` — иначе шаг кривой
  обнуляется и `level_for_xp` зацикливается навсегда.
- `get_xp_config()` вызывается в `lifespan`, чтобы плохие параметры роняли
  старт, а не первый запрос.

Пороги при дефолтах: `0, 200, 450, 763, 1154, 1642, 2252, 3015, 3969, 5161`.

Правишь формулу — дополняй параметризованную таблицу в `tests/unit/test_xp.py`,
а не переписывай её.

## Идемпотентность партии

Порядок шагов переставлять нельзя:

```python
game = await game_object.insert_if_absent(...)   # ON CONFLICT DO NOTHING
if game is None:
    already_counted = True
    game = await game_object.get_by_client_game_id(...)
    player = await player_object.get_by_id(...)
else:
    already_counted = False
    player = await player_object.add_xp(..., amount=game.xp_awarded)
await session.commit()
```

**Сначала вставка, потом начисление.** Если начислить первым, а вставка потом
упрётся в конфликт, опыт удвоится и откатывать придётся руками.

**`get_or_create` в духе Django здесь неверен**: между «посмотреть» и
«вставить» пролезает параллельный дубликат. `ON CONFLICT DO NOTHING` отдаёт
разрешение конфликта базе — это и есть корректная версия.

**На повторе опыт не пересчитывается формулой**, а читается из строки:
параметры кривой могли поменяться между попытками.

Корректно на `READ COMMITTED` (дефолт PostgreSQL). Уровень изоляции не менять.

## Регистрация и device_id

- **Токен не истекает**, но теряется: переустановка приложения или очистка
  данных — и прогресс не вернуть, в базе только хеш.
- `device_id` (на Android — `Settings.Secure.ANDROID_ID`) переживает
  переустановку и служит ключом идемпотентности регистрации.
- Известное устройство получает **свою же запись** и **свежий токен**;
  старый при этом отзывается. Ответ несёт `restored: true`.
- Без `device_id` каждый вызов создаёт нового игрока — ключа идемпотентности
  нет, повторить прежний ответ нечем.

**Цена, о которой надо помнить:** кто предъявит чужой `device_id`, получит на
него токен, то есть заберёт аккаунт. Закрывается только настоящим входом через
Google, а он за пределами итерации 1. Лидерборда нет, так что угнавший чужой
уровень в пасьянсе обманет только себя.

Токен: `secrets.token_urlsafe(32)`, в базе `hashlib.sha256(...).hexdigest()`.
Соли нет намеренно — это не пароль, а случайные 32 байта; поиск идёт по
уникальному индексу. `secrets.compare_digest` не нужен: сравнения секретов нет,
есть lookup по хешу предъявленного значения.

## Ручки

| Метод | Путь | Аутентификация | Ответ |
|---|---|---|---|
| POST | `/v1/players` | нет | 201 `PlayerRegisteredResponse` |
| GET | `/v1/players/me` | Bearer | `PlayerStateResponse` |
| PATCH | `/v1/players/me` | Bearer | `PlayerStateResponse` |
| DELETE | `/v1/players/me` | Bearer | `PlayerDeletedResponse` |
| POST | `/v1/games` | Bearer | 200 `GameResultResponse` |
| GET | `/v1/games` | Bearer | `GameListResponse` (limit ≤ 100) |
| GET | `/v1/games/{game_id}` | Bearer | `GameResponse` |
| PATCH | `/v1/games/{game_id}` | Bearer | `GameResponse` |
| DELETE | `/v1/games/{game_id}` | Bearer | `GameDeletedResponse` |

Путь `/me`, а не `/{player_id}`: администратора нет, игрок трогает только себя,
идентификатор в пути был бы декорацией.

**Семантика, которую нельзя нарушить:**

- `POST /v1/games` отдаёт **200 и на повторе тоже**. Повтор — не создание;
  факт создания несёт `already_counted`.
- **Удаление партии забирает начисленный за неё опыт.** Иначе в сумме остался
  бы опыт за партию, которой больше нет.
- **Смена `duration_ms` пересчитывает опыт**, разница атомарно переносится на
  игрока, `xp_formula_version` обновляется вместе с ним.
- **Чужая партия даёт 404, а не 403.** 403 сообщал бы, что она существует, —
  то есть позволял бы перебором нащупывать чужие идентификаторы.
- Неизвестный токен — **401**, а не 404. Текст одинаковый для «нет заголовка»
  и «токен не найден».
- `HTTPBearer(auto_error=False)` обязателен: со значением по умолчанию FastAPI
  отдаёт на отсутствующий заголовок 403.
- Лишние поля в теле запроса **игнорируются**, а не запрещаются: приложение на
  устройстве нельзя обновить по требованию.
- `duration_ms` ограничен сверху `2**63 - 1` — не игровое ограничение,
  а защита от переполнения BIGINT.

**`PATCH /v1/players/me` меняет `xp_total`** — единственное место во всём API,
где клиент пишет значение, которое иначе выводит сервер. Появится лидерборд —
эту ручку закрывать первой.

## Конвенция слоёв

```
app/api/        роуты: путь, Depends, одна строка вызова сервиса. Логики ноль
app/services/   оркестрация, границы транзакции, вызов чистых функций
app/single_object/  ВЕСЬ SQL. Импортировать services и views нельзя
app/views/      доменные объекты → схемы ответа, make_*_response_schema
app/schemas/    pydantic-контракты
app/exceptions.py  фабрики HTTPException: raise_*() -> NoReturn
```

Обязательные приёмы — нарушать их не надо:

1. **`raise_exception` у методов получения одного объекта.** Дефолт `True`:
   не нашли — бросили ошибку прямо в слое доступа, сервис не проверяет `None`.
   Кому отсутствие нормально (регистрация по `device_id`) — передаёт `False`
   явно. Перегрузки по `Literal[True]`/`Literal[False]` дают точный тип
   возврата, иначе `mypy --strict` требует лишних проверок.

2. **`response_model` в декораторе плюс аннотация возврата.** Первое задаёт
   контракт, второе требует `mypy --strict`. Класс в `response_model` — ровно
   тот, что возвращает соответствующий `make_*_response_schema`.

3. **Методы записи возвращают объект через детальный геттер.** `create` и
   `update` не отдают результат `RETURNING`, а перечитывают через `get_by_id`.
   Тогда запись и чтение не расходятся, а серверные умолчания (`created_at`)
   гарантированно заполнены — после `flush()` их в объекте нет, и обращение
   к ним в async даёт `MissingGreenlet`.

4. **Слой доступа отдаёт объекты, а не скаляры.** Исключение — счётчики
   (`count_games`, `count_by_player`).

5. **Виды принимают доменные объекты** (`Player`, `Game`), а не россыпь полей.

6. **Поля в схемах перечисляются руками**, `from_attributes` не включать:
   у `Player` есть `token_hash` и `device_id`, и автомаппинг по совпадению
   имён — ровно тот механизм, которым секрет уезжает в ответ.

7. **Чтение через `session.scalars(...).one_or_none()`**, а не
   `session.scalar(...)`: второй в асинхронном API типизирован как `Any`.
   Для перечитывания нужен `execution_options(populate_existing=True)` —
   иначе identity map отдаст устаревший объект.

8. **`session.get(Model, pk)` не использовать для свежего чтения**: он
   заглядывает в identity map и вернёт закешированный объект, не сходив в базу.
