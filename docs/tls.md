# Как включить HTTPS

Два способа получить TLS без покупки домена: сертификат прямо на IP-адрес ВМ
или бесплатный поддомен DuckDNS.

**Сейчас применён путь Б** — Caddy плюс бесплатный поддомен DuckDNS. Путь А
оставлен как справка: он пригодится, если однажды придётся обойтись без
доменного имени вовсе.

Домен в Yandex Cloud купить нельзя: Cloud DNS хостит зоны для доменов,
зарегистрированных где угодно ещё, а сам регистратором не является. Публичное
имя ВМ облако тоже не выдаёт — только внутреннее `*.internal`, снаружи оно
не резолвится.

## Про сертификаты на IP

Let's Encrypt выдаёт сертификаты на IP-адреса с
[15 января 2026](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability),
но с жёстким условием: только профиль `shortlived`, срок жизни **160 часов**
(чуть больше шести суток). Обычные 90-дневные сертификаты на IP не выдаются —
см. [таблицу профилей](https://letsencrypt.org/docs/profiles/).

Отсюда два следствия, которые стоит взвесить до, а не после:

- **Продлевать надо примерно раз в трое суток.** Сломается таймер — HTTPS умрёт
  в течение недели, и приложение перестанет работать. За этим проектом никто
  не следит, так что раздел «Мониторинг» ниже не украшение.
- **Caddy этого не умеет сам.** Он не поддерживает выбор ACME-профиля и отвечает
  `subject cannot have public IP certificate`
  ([caddyserver/caddy#7399](https://github.com/caddyserver/caddy/issues/7399)).
  Поэтому сертификат выпускает `acme.sh`, а Caddy только подаёт готовые файлы.

## Два пути

|  | [Сертификат на IP](#путь-а-сертификат-на-ip) | [Поддомен DuckDNS](#путь-б-бесплатный-поддомен-duckdns-рекомендуемый) |
|---|---|---|
| Срок сертификата | 6 суток | 90 дней |
| Продление | `acme.sh` + cron, раз в 3 суток | Caddy сам |
| Мониторинг | обязателен | не нужен |
| Внешние зависимости | нет | DuckDNS |
| Смена сервера | новая сборка клиента | правка записи DNS |
| Шагов в настройке | 4 плюс заглушка | 4 без фокусов |

**Если сомневаешься — сразу ко второму.** Первый честно работает, но требует
присмотра, которого у этого проекта не будет.

# Путь А: сертификат на IP

## Что понадобится

- **Статический IP.** Обязательно. Сертификат привязан к адресу, а эфемерный
  адрес в Yandex Cloud меняется при остановке и запуске ВМ — сертификат сразу
  станет недействительным, и заодно разъедется адрес, зашитый в клиенте.
- **Порты 80 и 443 открыты** в группе безопасности. 80 нужен и после выпуска:
  через него идёт проверка владения при каждом продлении.

### Сделать IP статическим

Консоль Yandex Cloud → **Virtual Private Cloud → IP-адреса** → найти
`158.160.29.18` → **Сделать статическим**. Адрес при этом не меняется.

Проверить, что получилось:

```bash
yc vpc address list
# в колонке reserved должно быть true
```

## Шаг 1. Каталоги и временный сертификат

Здесь курица и яйцо: Caddy не стартует без файлов сертификата, а `acme.sh` не
получит сертификат, пока Caddy не отдаёт файлы проверки на 80-м порту. Разрывается
самоподписанной заглушкой — Caddy поднимется с ней, а `acme.sh` тут же заменит
её настоящей.

```bash
ssh -i ~/.ssh/kosynka_deploy deploy@158.160.29.18
cd /opt/kosynka

mkdir -p certs acme-webroot

openssl req -x509 -newkey rsa:2048 -nodes -days 1 \
  -keyout certs/ip.key -out certs/ip.crt \
  -subj "/CN=158.160.29.18" \
  -addext "subjectAltName=IP:158.160.29.18"

echo "SITE_ADDR=158.160.29.18" > .env.site
chmod 600 .env.site
```

`certs/`, `acme-webroot/` и `.env.site` не в git и деплой их не трогает: `rsync`
идёт без `--delete` и с `--exclude='.env*'`.

## Шаг 2. Caddy в compose

**Эти правки коммитятся в репозиторий**, а не редактируются на сервере: `rsync`
перезаписывает `docker-compose.yml` при каждом деплое.

В `deploy/docker-compose.yml` у сервиса `app` убрать публикацию порта — наружу
теперь смотрит Caddy:

```yaml
  app:
    # было: ports: ["80:8000"]
    expose:
      - "8000"
```

И добавить сервис:

```yaml
  caddy:
    image: caddy:2.11
    restart: unless-stopped
    depends_on:
      - app
    env_file:
      - .env.site
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - ./certs:/certs:ro
      - ./acme-webroot:/var/www/acme:ro
      - caddy_data:/data
      - caddy_config:/config
    logging: *logging
```

и в конец, к `volumes:`:

```yaml
  caddy_data:
  caddy_config:
```

Новый файл `deploy/Caddyfile`:

```caddyfile
{
	# Автоматический выпуск отключён намеренно: на IP Caddy сертификат получить
	# не может, файлы готовит acme.sh. Без этой строки Caddy будет упорно
	# ходить в ACME и сыпать ошибками в лог.
	auto_https off
}

http://{$SITE_ADDR} {
	# Сюда acme.sh кладёт файлы подтверждения владения адресом.
	handle /.well-known/acme-challenge/* {
		root * /var/www/acme
		file_server
	}
	handle {
		redir https://{host}{uri} permanent
	}
}

https://{$SITE_ADDR} {
	tls /certs/ip.crt /certs/ip.key
	reverse_proxy app:8000
	encode gzip
	log {
		output stdout
		format console
	}
}
```

Закоммитить, влить в `main`, дождаться деплоя. Caddy поднимется с заглушкой:
браузер будет ругаться на недоверенный сертификат, но 80-й порт уже отдаёт
`/.well-known/acme-challenge/` — это всё, что нужно для следующего шага.

## Шаг 3. Выпустить настоящий сертификат

```bash
ssh -i ~/.ssh/kosynka_deploy deploy@158.160.29.18

curl https://get.acme.sh | sh -s email=ВСТАВЬ_СВОЙ_EMAIL
source ~/.bashrc

acme.sh --issue --server letsencrypt \
  -d 158.160.29.18 \
  -w /opt/kosynka/acme-webroot \
  --certificate-profile shortlived \
  --days 3
```

Что делают флаги:

- `--server letsencrypt` — по умолчанию acme.sh идёт в ZeroSSL, а IP-сертификаты
  умеет именно Let's Encrypt.
- `--certificate-profile shortlived` — **обязателен**. Без него Let's Encrypt
  откажет: на IP выдаются только короткоживущие сертификаты.
- `--days 3` — как часто пытаться продлить. У acme.sh есть
  [баг #6633](https://github.com/acmesh-official/acme.sh/issues/6633): для
  коротких сертификатов он показывает дату продления так, будто срок 90 дней.
  Реальным поведением управляет именно `--days`. Больше 5 ставить нельзя —
  сертификат протухнет раньше попытки.

Теперь разложить файлы туда, откуда их читает Caddy, и настроить перезапуск
после каждого продления:

```bash
acme.sh --install-cert -d 158.160.29.18 \
  --fullchain-file /opt/kosynka/certs/ip.crt \
  --key-file       /opt/kosynka/certs/ip.key \
  --reloadcmd      "cd /opt/kosynka && docker compose restart caddy"
```

`--install-cert` запоминает пути и команду: при каждом автоматическом продлении
файлы перезапишутся и Caddy перезапустится сам. Перезапуск занимает секунду —
для проекта, где игра работает офлайн, это ничто.

## Шаг 4. Продление

`acme.sh` при установке заводит cron для пользователя `deploy`. Проверить:

```bash
crontab -l | grep acme
# 26 0 * * * "/home/deploy/.acme.sh"/acme.sh --cron --home "/home/deploy/.acme.sh" > /dev/null
```

Задание запускается раз в сутки и продлевает сертификат, если ему больше трёх
дней. Прогнать вручную, не дожидаясь срока:

```bash
acme.sh --cron --force
```

### Мониторинг

При сроке в шесть дней запаса нет: молча сломавшееся продление убивает HTTPS
за неделю. Минимальная проверка, которую стоит завести хотя бы у себя в
календаре раз в месяц:

```bash
echo | openssl s_client -connect 158.160.29.18:443 2>/dev/null \
  | openssl x509 -noout -dates -subject
```

`notAfter` должен быть в пределах ближайших шести суток и **сдвигаться** от
проверки к проверке. Если дата замерла — продление не работает, смотри
`~/.acme.sh/acme.sh.log`.

## Проверка

```bash
curl -v https://158.160.29.18/healthz
# должно быть: SSL certificate verify ok, {"status":"ok"}

curl -sI http://158.160.29.18/healthz | head -1
# должно быть: HTTP/1.1 308 Permanent Redirect
```

---

## Если сломается

| Симптом | Причина |
|---|---|
| `subject cannot have public IP certificate` | Забыт `--certificate-profile shortlived`. |
| Проверка не проходит, 404 на challenge | Caddy не отдаёт `/var/www/acme` — сверь `-w` в acme.sh с томом в compose. |
| `curl: SSL certificate problem: self signed` | Заглушка из шага 1 не заменена: `--install-cert` не выполнялся или пути разошлись. |
| HTTPS отвалился через неделю | Не отработал cron. `crontab -l`, затем `~/.acme.sh/acme.sh.log`. |
| Сертификат стал недействителен после перезапуска ВМ | IP был эфемерным и сменился. Сделать статическим и выпустить заново. |
| Caddy не стартует | Нет `certs/ip.crt` или `certs/ip.key` — вернись к шагу 1. |

# Путь Б: бесплатный поддомен DuckDNS (рекомендуемый)

Проще предыдущего на порядок: обычный **90-дневный** сертификат, Caddy получает
и продлевает его сам. Ни `acme.sh`, ни заглушки, ни таймеров, ни мониторинга.

`duckdns.org` есть в Public Suffix List, поэтому лимиты Let's Encrypt считаются
на твой поддомен персонально, а не делятся со всеми пользователями сервиса.
У `nip.io` и `sslip.io` этого свойства нет — там квота общая, и упереться в неё
можно без своей вины.

### Шаг 1. Имя

Зайти на [duckdns.org](https://duckdns.org) через GitHub-аккаунт, завести имя
(например `kosynka`) и вписать в поле IP **публичный IPv4 ВМ** — `158.160.29.18`.
Поле IPv6 оставить пустым. Бесплатно, без срока. Со страницы забрать **token** —
он понадобится дальше.

> Адрес вписывать **руками**. Кнопка автозаполнения на странице подставляет тот
> адрес, с которого ты сейчас зашёл, то есть домашний, а не серверный.

Дождаться, пока запись разойдётся:

```bash
dig +short kosynka.duckdns.org
# 158.160.29.18
```

Это обязательно **до** первого запуска Caddy: он проверяет владение именем
через HTTP-01, и без корректной A-записи упрётся в ошибку ACME.

### Шаг 2. Обновление записи

Даже со статическим IP полезно: запись остаётся свежей, а при смене адреса
чинится сама. Крон заводится **на сервере**, от имени `deploy` — с пустым `ip=`
DuckDNS берёт адрес источника запроса, поэтому та же команда, запущенная с
ноутбука, направит домен на твой домашний интернет:

```bash
crontab -e
```

добавить строку (`ip=` пустой — DuckDNS подставит адрес, с которого пришёл запрос):

```
*/5 * * * * curl -fsS "https://www.duckdns.org/update?domains=kosynka&token=ТВОЙ_ТОКЕН&ip=" > /dev/null
```

Токен виден в `crontab -l`; если это смущает, положи строку в скрипт
`/opt/kosynka/duckdns.sh` с правами 700 и вызывай его.

### Шаг 3. Настройки на сервере

```bash
ssh -i ~/.ssh/kosynka_deploy deploy@158.160.29.18
cd /opt/kosynka

cat > .env.site <<EOF
SITE_ADDR=kosynka.duckdns.org
ACME_EMAIL=ВСТАВЬ_СВОЙ_EMAIL
EOF

chmod 600 .env.site
```

`ACME_EMAIL` — туда Let's Encrypt пришлёт предупреждение, если продление
однажды перестанет работать.

### Шаг 4. Caddy в compose

**Правки коммитятся в репозиторий**, а не редактируются на сервере: `rsync`
перезаписывает `docker-compose.yml` и `Caddyfile` при каждом деплое.

У сервиса `app` убрать публикацию порта — наружу теперь смотрит Caddy:

```yaml
  app:
    # было: ports: ["80:8000"]
    expose:
      - "8000"
```

Добавить сервис:

```yaml
  caddy:
    image: caddy:2.11
    restart: unless-stopped
    depends_on:
      - app
    env_file:
      - .env.site
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      # В caddy_data лежат сертификаты и ACME-аккаунт. Терять этот том нельзя:
      # после удаления Caddy выпустит всё заново и может упереться в лимит
      # Let'''s Encrypt (50 сертификатов на домен в неделю).
      - caddy_data:/data
      - caddy_config:/config
    logging: *logging
```

и в конец, к `volumes:`:

```yaml
  caddy_data:
  caddy_config:
```

Новый файл `deploy/Caddyfile` — весь целиком:

```caddyfile
{
	email {$ACME_EMAIL}
}

{$SITE_ADDR} {
	reverse_proxy app:8000
	encode gzip
	log {
		output stdout
		format console
	}
}
```

Всё. `auto_https` не отключается, `tls` с путями к файлам не нужен: Caddy видит
доменное имя как адрес сайта и получает сертификат сам, при первом запуске.

### Шаг 5. Открыть 443

В группе безопасности Yandex Cloud — входящее правило TCP `443` с источником
`0.0.0.0/0`. Порт 80 оставить: через него идёт проверка HTTP-01 и редирект на
HTTPS, который Caddy настраивает автоматически.

### Проверка

```bash
curl -v https://kosynka.duckdns.org/healthz
# SSL certificate verify ok, {"status":"ok"}

curl -sI http://kosynka.duckdns.org/healthz | head -1
# HTTP/1.1 308 Permanent Redirect
```

Первый запрос после деплоя может занять несколько секунд — Caddy в этот момент
получает сертификат. Если не вышло, смотреть `docker compose logs caddy`.

### Чем платим

Внешней зависимостью: ляжет DuckDNS — имя перестанет резолвиться. Для этого
проекта последствия мягкие, игра работает офлайн, а сеть опциональна. То есть
недоступность DNS означает, что опыт не синхронизируется, а не что бабушка
не может разложить пасьянс.
